# Synthetic evaluation

`evaluation/inputs/` contains 18 valid V1 incident bundles. `evaluation/labels/` holds expected rule classes, separate evidence ID groups for every expected finding, and prohibited conclusions. Corpus version 2 records synthetic origin, template, split and version in `manifest.json`. Ten cases are training/regression examples and eight distinct templates were assigned to holdout. These are small engineered examples, not representative production data. The holdout results have already been inspected during INV-004; treat them as regression cases for future changes and add fresh holdout templates before any generalization claim.

Run the offline evaluation with `uv run investigerror evaluate --mode rules --split all --out artifacts/evaluation.json`. It writes JSON metrics and a Markdown human review sheet. Per-class precision and recall count exact finding/evidence groups, including multiple findings of one rule. True negatives count cases with no expected or predicted finding of that class. Missing, unexpected or prohibited findings fail the quality gate with exit 4 while preserving the report. Exit 0 means the software passed these synthetic checks, not that a model was accurate. The default run makes no provider call and marks model quality, latency, tokens and cost unmeasured.

For an explicitly authorized live comparison, configure `ANTHROPIC_API_KEY` and `AI_MODEL`, then run `uv run investigerror evaluate --mode live --allow-cloud --split holdout --trials 2 --out artifacts/live-evaluation.json`. Each trial gives the same selected, sanitized records to (1) a generic prompt without computed findings and (2) the structured evidence prompt with findings. Both use the same model, output budget and explanation schema. Rules have no provider token cost. The selected records are chosen once for the pair. Expected labels, manifest entries, filenames and scenario switches are never included in either model payload. Natural error codes in the evidence remain visible. Inspect the context and budget before authorizing a live run.

The runner checks schema and cited IDs, and records provider latency/tokens when available. It rechecks each exact outbound payload against the 100-record and 40,000-character limits. A provider request failure stops further calls, writes a partial or failed JSON result and review sheet, and exits 3; completed calls and their known usage remain in the output. Failed request usage remains unknown. A valid reference means only that the cited record was supplied. Human reviewers must assess whether each claim is supported, count unsupported claims, rate usefulness 0-2 (0 unusable, 1 partly useful, 2 useful), and rate verification steps 0-2 (0 absent, 1 vague, 2 specific and feasible). The generated sheet leaves these fields `unreviewed`. Do not treat unreviewed fields as zero. Cost is unknown until a pricing source and actual usage are configured. Repeat a subset of live cases to inspect variability; no live model scores are published by this project yet.

The corpus generator is `scripts/build_corpus.py`; inputs and labels are separate files. Invalid parser/size cases remain in unit tests and do not count toward the 18 valid cases.
